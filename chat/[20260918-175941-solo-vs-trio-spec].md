# 1vs3（ボス vs 三人組）モード 仕様書

対象：IDマッチ（ロビーID共有）での 1vs3 実装。ランダムマッチ対応は次段階。

作成：2026-09-18 / 最終更新：2026-09-18（ボス能力「制圧」を追加） / ステータス：仕様確定（実装前）

---

## 1. 目的とスコープ

4人対戦を「1人（ボス）」対「3人（トリオ）」の非対称戦にする。
ボス側は不利を補う強化と、専用能力「制圧」を持つ。トリオ側は互いに攻撃が当たらない。

### やること（今回）

- IDマッチ（手動ロビー）での 1vs3 モード
- トリオ内の同士討ち無効化
- チーム単位の勝敗判定と結果表示
- ボス強化（HP・攻撃力・SP獲得速度・SP最大値）
- ボス専用能力「制圧」（範囲内の敵を操作不能にする）

### やらないこと（次段階以降）

- ランダムマッチでの 1vs3（§13-3 に見通しを記載）
- 残機制との併用（§13-1 で v1 は排他とする）
- ボスのサイズ強化（§8 の注記のとおり v1 では見送る）
- 2vs2 など他の非対称編成（データモデルは拡張可能にしておく）

## 2. 決定事項

| # | 論点 | 決定 |
|---|---|---|
| 1 | ボス役の決め方 | **開始時にホストがランダム抽選** |
| 2 | 開始可能人数 | **4人ちょうど必須**（3人以下では開始不可） |
| 3 | 勝敗・順位 | **チーム勝利。勝利チーム全員1位、敗北チーム全員2位** |
| 4 | トリオ同士の攻撃 | **ダメージは発生しない**（物理的な弾き合いは残す／§7-1） |
| 5 | `PROTOCOL_VERSION` | **3 → 4 に上げる**（開発中のため、古いタブを弾くコストが無い） |
| 6 | SPゲージ | **ボスのみ最大200。100で通常必殺、200で制圧の2段階** |
| 7 | 制圧の効果 | **範囲内の敵は移動も必殺技も、全入力を受け付けない** |
| 8 | 独楽モードでの制圧 | **自動追尾も停止する**（その場で回るだけになる） |
| 9 | 制圧の範囲判定 | **発動の瞬間に1回だけ**。以降ボスが離れても効果は続く |
| 10 | 100と200の撃ち分け | **ボタンを分けて明示的に選ぶ**（`INPUT` に新アクションを追加） |

## 3. 用語とデータモデル

### 3-1. 用語

| 用語 | 意味 |
|---|---|
| ボス（solo） | 1人側のプレイヤー。`team = 0` |
| トリオ（trio） | 3人側のプレイヤー。`team = 1` |
| soloMode | この 1vs3 ルールの ON/OFF。`gameMode`（剣/独楽）・`livesMode`（残機制）と同列の独立トグル |
| 制圧 | ボス専用能力。範囲内の敵を一定時間操作不能にする |

### 3-2. 部屋（ロビー）に増えるフィールド

`livesMode` と完全に同じ扱いにする（既存の実装パターンを踏襲）。

```js
soloMode: boolean   // 既定 false
```

`snapshot()` に含めてゲストへ配信する。ロビーの名簿（`players[]`）には**陣営を持たせない**
— 抽選は試合開始時に行うため、ロビー中は誰がボスになるか未定。

### 3-3. 試合設定（PREPARE / InitializeMultiplayer）に増えるフィールド

```js
{
  matchId, gameMode, livesMode,
  soloMode: true,                    // 新規
  soloBuff: {                        // 新規（soloMode が false のときは null）
    hpMultiplier: 3.0,
    attackMultiplier: 1.3,
    spGainMultiplier: 1.5,
    maxSp: 200,
    suppressRadius: 8.0,
    suppressDuration: 10.0
  },
  players: [
    { playerId, slotIndex, spawnIndex, swordData,
      team: 0 }                      // 新規：0 = ボス / 1 = トリオ
  ]
}
```

`team` は**プレイヤーごとの整数**にする。`soloPlayerId` を1個持つ形でも 1vs3 は表現できるが、
`team` なら 2vs2 や 1vs1vs2 にそのまま拡張できるため、こちらを採る。

Unity 側は `MultiplayerPlayerConfig.team` と `MultiplayerConfig.soloMode` / `soloBuff` を追加する。
`team` は試合中に変化しないので、`MultiplayerSync`（毎フレームの同期）には**含めない**。

## 4. プロトコル変更

**`PROTOCOL_VERSION` を 3 → 4 に上げる。**

理由：`soloMode` を知らない旧クライアントが同席すると、ボスのHPバー・SPゲージが
ローカルの上限で頭打ちになり、**試合中ずっと誤った数値を表示する**（§8 の注記を参照）。
勝敗自体はホスト権威なので狂わないが、見た目が嘘をつく状態は再現しにくい不具合になる。

開発中でありデプロイのたびに全員がリロードするため、古いタブを弾くコストは実質ゼロ。
既存の `REJECT` 経路（「ゲームのバージョンが異なります。再読み込みしてください。」）がそのまま機能する。

## 5. ロビー仕様

### 5-1. トグル

- ホストのみ操作可能。手動ロビー（`autoStart === false`）のみ表示
- `setSoloMode(enabled)` は `phase === 'LOBBY'` のときだけ許可し、`resetReady()` を伴う
  （＝ルール変更で全員の準備完了を解除する。`setGameMode` / `setLivesMode` と同じ規約）

### 5-2. 開始条件

`canStart()` に条件を追加する。

```
soloMode が true のとき： players.length === 4 を必須とする
```

3人以下の場合、開始ボタンは押せず、ロビーには「1vs3 には4人必要です（あと○人）」と表示する。

### 5-3. 表示

- ルール欄に「👑 1 vs 3」バッジを出す
- 「開始時に1人がランダムでボス側になります」と明記する

## 6. 試合開始の仕様

### 6-1. 抽選

ホストの `RoomSession.prepare()` で、スポーン順のシャッフルと同じ場所で行う。

1. 4人から1人を一様ランダムで選び `team = 0`、残り3人を `team = 1` とする
2. 抽選結果は `PREPARE` パケットで全員に配る（ゲストは抽選しない）

**乱数は注入可能にする。** 現在 `prepare()` は `Math.random()` を直接呼んでいるためテストできない。
`now` と同じ要領で `random = Math.random` をコンストラクタ引数にし、テストから固定値を渡せるようにする。
スポーン順のシャッフルも同じ乱数源に寄せる。

### 6-2. スポーン位置

ボスとトリオが入り混じって始まらないよう、**陣営ごとに配置を固定し、陣営内だけシャッフルする**。

- `spawnIndex = 0` をボス専用とする
- トリオには `spawnIndex = 1, 2, 3` をシャッフルして割り当てる

Unity 側は `SceneController` に 1vs3 専用レイアウトを追加する。

```csharp
public Vector3[] sword1v3Positions;      // [0]=ボス, [1..3]=トリオ
public Vector3[] koma1v3Positions;
public Transform[] sword1v3SpawnPoints;  // シーン上で視覚的に置く場合（既存の仕組みと同じ）
public Transform[] koma1v3SpawnPoints;
```

`GetSpawnPositions(playerCount)` に 1vs3 用の分岐を足す（未設定なら既存の4人用レイアウトへフォールバック）。
推奨配置は「ボスが片側、トリオが反対側に横並び」。剣モードは左右対向、独楽モードは上下対向を想定。

## 7. 戦闘仕様（陣営）

### 7-1. 同士討ちの無効化

**ダメージのみ無効。物理的な衝突・弾き合いは従来どおり発生する。**

理由：コライダーのレイヤーを分けて貫通させると、トリオ3人が同じ座標に重なって団子になり、
見た目にも操作感にも破綻が出る。ぶつかって弾かれるが減らない、という挙動が自然。

判定は**2箇所**に置く。

| 場所 | 役割 |
|---|---|
| `MatchRules.ResolveStep()` | **権威**。同一チームの `Hit` を裁定前に除外する。テスト対象 |
| `MultiplayerManager.QueueHit()` | 早期リターン。ダメージ数値ポップアップ・クリティカル演出を出さないため |

`MatchRules` 側に必ず置くこと。ここが唯一の正本であり、Unity の当たり判定コールバックが
どう呼ばれても結果が変わらないという既存の設計原則を崩さない。

同士討ちで**発生しないもの**：ダメージ、SP獲得（被弾由来）、撃破数の加算、クリティカル演出、ダメージポップアップ。
**発生するもの**：弾き合いの力、接触音・火花（`clashSeq` 由来の演出）。

### 7-2. ターゲット選定

`BattlePolicies.Target()` に陣営を渡し、**味方を候補から除外**する。

```csharp
public sealed class TargetCandidate {
    public readonly string Id;
    public readonly int Slot;
    public readonly int Team;   // 追加（既定 0 で既存の呼び出しは無改変）
    ...
}
```

結果として：

- トリオ3人 → 常にボスを狙う（候補が1人しかいないため、ヒステリシスは実質無効化される）
- ボス → トリオのうち最も近い相手。既存の 0.64 倍ヒステリシスがそのまま効く

独楽モードの自動追尾（`SwordController.komaHomingForce`）は `enemyTarget` を見ているので、
この変更だけで味方に突っ込まなくなる。独楽モードでも 1vs3 は成立する。

## 8. ボス強化

適用は **Unity 側の剣生成時**（`CreateSword`）に1回だけ行う。
倍率は `soloBuff` として設定に載せ、ホストとゲストが同じ値を使う。

| パラメータ | 初期提案値 | 適用先 |
|---|---|---|
| `hpMultiplier` | 3.0 | `MatchRules` に渡すHPと `SwordBattle.maxHp` |
| `attackMultiplier` | 1.3 | `SwordBattle.attack` |
| `spGainMultiplier` | 1.5 | 時間経過・被弾によるSP獲得量 |
| `maxSp` | 200 | `SwordBattle.maxSp` |

いずれも**要調整**。まず 1vs3 が成立することを確認し、実際に遊んでから詰める。

`spGainMultiplier` は当初 2.0 を提案したが、2段階ゲージの決定を受けて **1.5 に下方修正**した。
2.0 だとボスが通常必殺技を約10秒ごとに撃ててしまい、トリオ側の20秒に対して手数が倍になる。

### サイズ強化を見送る理由

`SwordBattle` は既に `baselineScale` を記録・復帰する仕組みを持ち、巨大化一回転は
`originalScale` を退避して戻している。生成後に `localScale` を直接いじると、
**巨大化一回転から戻った瞬間にボスだけ素のサイズに戻る**。
既存の必殺技に手を入れずに済ませるため、v1 ではサイズ強化を入れない。

### 注記：クライアント全員に適用しないと表示が壊れる

以下2箇所がローカルの上限で頭打ちにするため、`soloBuff` は**全クライアントで適用する**必要がある。

| 箇所 | 内容 |
|---|---|
| `SwordBattle.ApplyMultiplayerHealth` | `hp = Mathf.Clamp(health, 0, maxHp)` — `maxHp` が素の値だとHPバーが誤表示 |
| `SwordBattle.ApplyMultiplayerVisuals` | `currentSp = Mathf.Clamp(sp, 0, maxSp)` — `maxSp` が100だとSPゲージが頭打ち |

### 注記：`MatchRules` のHP上限

`MatchRules` は `hp < 1 || hp > 1000` で例外を投げる。強化後は最大3000になるため、
**上限を 4000 に緩和する**。既存の有効な入力（1000以下）の挙動は変わらない。
`validateSword`（素の剣データの検証）は 1000 のまま据え置く。強化は剣データではなく試合設定側の話。

## 9. ボス能力「制圧」

### 9-1. SPゲージの2段階化

| 項目 | 値 |
|---|---|
| ボスの `maxSp` | 200 |
| 通常必殺技の閾値・消費 | **100**（全員共通） |
| 制圧の閾値・消費 | **200**（＝満タン） |
| 消費の仕方 | どちらも**全消費**（既存の `currentSp = 0f` を踏襲） |

**新フィールド `ultimateSp`（既定 100）を `SwordBattle` に追加し、`UltimateThreshold` の参照先を
`maxSp` から `ultimateSp` に変える。**

```csharp
// 変更前： public float UltimateThreshold => SwordController.isKomaMode ? 70f : maxSp;
// 変更後： public float UltimateThreshold => SwordController.isKomaMode ? 70f : ultimateSp;
```

通常プレイヤーは `maxSp == ultimateSp == 100` なので**挙動は1ビットも変わらない**。

> **既存の食い違い（要修正）**
> 必殺技の発動判定は2箇所にあり、別々の値を見ている。
> UI（ボタン表示・オーラ）は `UltimateThreshold`、ホストの許可判定は
> `BattlePolicies.UltimateAction` の **`sp >= 100` べた書き**。
> `maxSp` を200にするだけだと「ボタンは200まで出ないのに内部的には100で撃てる」状態になる。
> **閾値は `BattlePolicies` に引数で渡すこと。**

### 9-2. 発動条件

すべて満たしたときのみ発動する。

- `soloMode` かつ `team == 0`（ボス本人）
- 対戦中（`IsPlaying`）かつ生存
- 突進中（`isDashing`）でない
- `currentSp >= maxSp`（200）
- 自身が制圧されていない

### 9-3. 効果

| 項目 | 内容 |
|---|---|
| 対象 | **発動の瞬間**にボスの `currentCenterPosition` から半径 `suppressRadius` 以内にいる、生存している敵チームのプレイヤー |
| 判定タイミング | **発動時に1回だけ**。以降ボスが離れても、対象が範囲外へ出ても効果は続く |
| 効果 | `suppressDuration` 秒間、対象は**全入力を受け付けない**（移動・必殺技・制圧のすべて） |
| 独楽モード | 対象は**自動追尾も停止**し、その場で回るだけになる（回転力には触らないので見た目は回り続ける） |
| 発動中の技 | **キャンセルしない**。突進中・分身中の相手はその技を完走する |
| 物理 | 重力・慣性・衝突・弾き合いはすべて通常どおり継続する |
| 味方・自分 | 対象外 |

距離は `transform.position`（柄の位置）ではなく **`currentCenterPosition`** で測る。
剣モードでは同値、独楽モードでは重心になり、縦長の剣画像でも判定がぶれない。
比較は2Dで行い、z は無視する。平方根を避けるため**距離の二乗で比較**する（`Target()` と同じ作法）。

### 9-4. 判定を置く場所

既存のアーキテクチャに合わせ、**純粋ロジック層に置いてテスト可能にする**。

```csharp
// BattlePolicies に追加：範囲内の敵IDを返す純粋関数
public static string[] SuppressTargets(float bossX, float bossY, float radius,
    IEnumerable<TargetCandidate> candidates, string bossId, int bossTeam);

// 既存2関数に stunned を追加（既定 false で既存の呼び出しは無改変）
public static string PrimaryAction(bool koma, float sp, bool started, bool alive, bool dashing,
    bool right, bool stunned = false);
public static string UltimateAction(bool koma, float sp, bool started, bool alive, bool dashing,
    bool stunned = false, float ultimateSp = 100f);
```

ホスト側の流れ：

1. `ReceiveMultiplayerInput` が `SUPPRESS` を受け取る
2. `BattlePolicies.SuppressTargets()` で対象を決める
3. 対象ごとに `suppressUntil[playerId] = Time.unscaledTime + suppressDuration` を記録
4. 毎 `FixedUpdate` で `suppressUntil` から `stunned` を組み立てる（`invulnerable` と同じ作り）
5. `stunned` を `BattlePolicies.PrimaryAction` / `UltimateAction` に渡す → `null` が返り、入力が捨てられる

入力の門番は既に `ReceiveMultiplayerInput` → `BattlePolicies` の一本道なので、新しい抜け道は生まれない。

独楽の自動追尾停止は `SwordController` に `stunned` フラグを足し、`FixedUpdate` の
**追尾力にだけ**条件を付ける（回転力・重心設定には触らない）。

### 9-5. 入力プロトコル（新アクション `SUPPRESS`）

100と200を明示的に撃ち分けるため、`INPUT` に新しい `action` を1つ追加する。
変更は4ファイルで、いずれも**既存の分岐に並べて足すだけ**。

| ファイル | 変更 |
|---|---|
| `MultiplayerManager.cs`（送信） | `SubmitLocalSuppress()` を追加し、`Emit("INPUT", { action = "SUPPRESS" })` |
| `RoomSession.js` `unityEvent()` | `isSuppress = data.action === 'SUPPRESS'` の分岐を追加 |
| `HostRoom.js` `acceptInput()` | 同上。正規化した `{ playerId, matchId, seq, action: 'SUPPRESS' }` を返す |
| `MultiplayerManager.cs`（受信） | `ReceiveMultiplayerInput` に `SUPPRESS` の分岐を追加 |

連番（`seq`）と40msの連打制限は既存の仕組みをそのまま通す。

### 9-6. 同期と表示

- `MultiplayerPlayerState` に `suppressedRemaining`（float）を追加。既存フィールドは変更しない
- 対象者の頭上に「操作不能」表示と残り時間。**新規に生成して `StopCurrent()` で破棄**する
- 既存のエフェクト・パーティクル・prefab・マテリアルには触らない

### 9-7. ボタン

既存の `specialAttackButton` はシーンに1つだけ置かれた共有ボタンで、
`MultiplayerManager` が各 `SwordBattle` に割り当てている。キーボードは Space が割り当て済み。

**制圧ボタンは実行時に生成する**（シーンには触らない）。

| | 通常必殺技 | 制圧 |
|---|---|---|
| ボタン | 既存の共有ボタン（変更なし） | **実行時生成**。ボス本人にだけ、SP200で表示 |
| キー | Space（既存） | 別キーを割り当てる（例：左Shift） |

生成したボタンは `StopCurrent()` で破棄する。

## 10. 勝敗と結果

### 10-1. 決着条件

`MatchRules` の終了判定をチーム対応にする。

```
現在： 生存プレイヤーが 1 人以下になったら終了
変更： 生存しているチームが 1 つ以下になったら終了
```

- 生存チームが1つ → そのチームの勝利
- 生存チームが0（相打ちで同時全滅） → 引き分け

`teams` を渡さない（＝個人戦）ときは現在のコードをそのまま通すので、既存の挙動と完全に一致する。

### 10-2. 順位

| 状況 | 順位 |
|---|---|
| 勝利チーム | 全員 **1位**（途中で撃破された人も含む） |
| 敗北チーム | 全員 **2位** |
| 引き分け | 順位は付けず、`draw` フラグで表示する（既存どおり） |

個人戦の順位付けロジックには**一切触れない**。チーム戦のときだけ、決着時に上書きする。
`eliminationTick` と `eliminationReason` は従来どおり個人単位で記録する。

### 10-3. 結果データ

`MatchRules` と `MultiplayerResult` に `winnerTeam` を追加する（引き分けは -1）。

`winnerId` の扱い：

- soloMode が false → 従来どおり勝者の `playerId`
- soloMode が true かつボス勝利 → ボスの `playerId`
- soloMode が true かつトリオ勝利 → **null**（勝者が複数のため）

React 側は soloMode のとき `winnerTeam` を見る。結果画面の背景に使う剣画像は、
トリオ勝利時は「勝利チームのうち最後まで生存していた1人」の剣を使う。

## 11. 例外時の挙動

| 事象 | 挙動 |
|---|---|
| トリオの1人が切断 | 既存の `FORFEIT` で即脱落。1vs2 として続行する（人数不利の補正はしない） |
| トリオ全員が切断 | ボスの勝利として決着 |
| ボスが切断 | トリオの勝利として決着 |
| 読み込み中（LOADING / COUNTDOWN）に誰かが切断 | 既存どおり `ABORT` して全員ロビーへ戻る。**抽選もやり直し**になる |
| ロビーで4人未満になった | `canStart` が false になり開始できない。ルールは保持したまま待機 |
| 制圧中の相手が撃破された | 効果はそのまま消える（`isDead` の時点で入力経路が閉じるため追加処理は不要） |
| 制圧中に試合が終了した | `StopCurrent()` / `FinishMultiplayer` で `suppressUntil` を破棄する |

再戦時（`returnToLobby` 後に再度開始）は**毎回抽選し直す**。同じ人が連続でボスになることもある。

## 12. UI 仕様

### 12-1. ロビー（LobbyScreen）

- ルール欄に `1 vs 3: ON / OFF` トグル（ホストのみ・手動ロビーのみ）
- ON のとき、説明文を「1人 vs 3人。3人側は同士討ちしません。ボスは開始時にランダムで決まります」に差し替える
- 4人未満のときは開始ボタンを無効化し、不足人数を表示する

### 12-2. 対戦中（Unity HUD）

- ボスのHPバーに識別マーク（王冠アイコンなど）を付ける
- ボスのSPゲージは最大200として表示する（`spGaugeBar.maxValue = maxSp` が既にあるので自動追従）
  - 100の位置に区切り線を入れ、2段階であることを示す
- トリオ3人は既存のプレイヤー色（P1〜P4）を維持する
  — 陣営で色を統一すると誰が誰か分からなくなるため色は変えない
- 制圧された側：頭上に「操作不能」と残り時間。自分が対象なら必殺技ボタンを非表示にする

### 12-3. 結果（ResultScreen）

- 見出し：`YOU WIN!!` / `YOU LOSE` / `DRAW`
- 勝者欄：「ボスの勝利」「3人組の勝利」
- 順位表に**陣営列**を追加（👑 ボス / 👥 トリオ）。並び順は 勝利チーム → 敗北チーム、
  チーム内は与ダメージの多い順

## 13. 既存機能との相互作用

### 13-1. 残機制（livesMode）との併用

**v1 では排他とする。** ロビーで両方を同時に ON にできないようにする。

理由：ボスの実効HPが `素のHP × 3本 × 3.0倍` になり、調整軸が一気に増える。
1vs3 単体のバランスが固まってから改めて検討する。

実装：`setSoloMode(true)` は `livesMode` を false にし、その逆も同様にする（後勝ち）。

### 13-2. 剣モード / 独楽モードとの併用

**どちらとも併用可。** `soloMode` は `gameMode` と直交する独立トグル。

### 13-3. ランダムマッチ（次段階）

待合所（`api/match`）は**部屋のルールで絞り込みをしていない**（`store.candidates` は
phase・人数・作成時刻・除外リストだけを見る）。`matchSeeker` のコメントにあるとおり
「他人の部屋に入った場合はその部屋のルールに従う」設計なので、
**待合所側の変更なしで 1vs3 のランダムマッチは成立する**。

必要なのは以下のみ：

- `useRandomMatch` の `createRoom` に `soloMode` を渡す（`gameMode` と同じ経路）
- `targetSize = 4` を必須にする
- 自動開始（`autoStartTick`）の「人数が埋まらなければ切り上げて開始」を、
  soloMode の部屋では**無効にする**（3人で始まると 1vs2 になるため）

## 16. 未決事項

1. **バランス数値**（HP×3.0 / 攻撃×1.3 / SP獲得×1.5 / 制圧半径8.0 / 効果時間10.0秒）はすべて仮。実際に遊んで調整する
   - 効果時間10秒は、SP満タンまで約27秒（`passiveSpFill 5 × 1.5 = 7.5/秒`）に対して**拘束率が約37%**になる。
     強すぎる場合に回す調整つまみは、優先順に `spGainMultiplier`（溜め時間）→ `suppressRadius`（巻き込む人数）→ `suppressDuration`
2. **制圧ボタンのキー割り当て** — 左Shift を提案。他に空いているキーがあれば変更可
3. **制圧の視覚表現** — 発動時にボスを中心とした波紋を出すか。出す場合は新規生成のみで既存エフェクトには触らない
4. **時間制限の有無** — 現在このゲームに試合時間の上限は無い。ボスのHPが3倍になることで試合が長引く場合、時間切れ判定の追加を検討する
5. **トリオ側にも調整を入れるか** — まずはボス強化のみで様子を見る
