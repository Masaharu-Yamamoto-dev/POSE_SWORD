# POSE SWORD：ランダムマッチ 仕様書・設計計画案

作成日：2026-09-12。現行ソース（2〜4人可変対戦への統合後）を確認して作成した計画案。ゲーム実装はまだ変更していない。

## 1. 目的と確定事項

ロビーIDを知らない相手とも対戦できるようにする。ユーザーとの確認で決まった前提は次のとおり。

| 項目 | 決定 |
| --- | --- |
| 待ち合わせの土台 | **Vercel関数 + 外部KV（Upstash Redis）** |
| 同時待機人数 | **上限を設ける**。超えた人は待機できず「混雑中」として断る |
| 人数 | プレイヤーが「2人戦」「4人戦」を選んでキューに並ぶ |
| ゲーム種別 | マッチ条件にしない。入った部屋（ホスト）のモードに従う |
| 対戦後 | 「同じ面々で再戦」と「別の相手を探す」の両方を用意する |

初期リリースの範囲外：レート・実力マッチング、地域／レイテンシ考慮、フレンド招待、観戦、常設ランキング。

### 1.1 「最大待機人数」の定義

**有効な入場券の数**を待機人数とする。内訳は「相手を探している人」と「ホストとして人を待っている人」の合計で、**対戦が始まった人は券を返すので数に入らない**。上限は環境変数 `MATCH_MAX_WAITING` で指定し、実行中に変更できる。

この上限は同時に**コストの上限**でもある。第4.5節のとおり、KVへのコマンド数は「待機人数 × ポーリング頻度」でほぼ決まるため、この値が無料枠を超えない唯一の歯止めになる。

## 2. 仕組みの考え方

PeerJS のクラウドブローカーは接続中のpeer一覧を公開しない。したがって「待っている人」を見つけるには、**接続先になれるホストが自分のロビーIDを外部に広告する**しかない。

- ホスト（部屋を作った人）だけが `roomId` を待合所へ登録する。
- 参加したい人は待合所から候補IDを受け取り、**既存の入室処理（`JOIN`→`ACCEPT`／`REJECT`）でそのまま入る**。
- 待合所は掲示板でしかない。名簿・準備・試合進行はこれまでどおりホストが持つ（P2Pのまま）。

ただし人数の上限を課すため、**探している人も含めて全員が入場券を持つ**。券はマッチングを始めるときに受け取り、抜けるときに返す。券を持たない要求は受け付けない。

```
                    ┌──────────── Vercel関数 /api/match ────────────┐
  ブラウザ ────────→│ enter  入場券を発行（上限に達していれば拒否）  │──→ Upstash Redis
   （待機者）  ←────│ poll   券の更新＋部屋の登録／候補の取得        │←──（券・部屋・待機数）
                    │ leave  券と部屋の後始末                        │
                    └───────────────────────────────────────────────┘
        ↓ 候補のロビーIDを受け取ったら、以降はPeerJSで直接つながる（サーバーを介さない）
```

## 3. プレイヤーから見た流れ

1. タイトルで「ランダムマッチ」を押し、**ルール（剣／独楽）と人数（2人戦／4人戦）**を選ぶ（装備中の剣でそのまま参戦する）。選んだルールは自分が部屋を立てたときに使われ、相手の部屋に入った場合はその部屋のルールに従う。
2. 「対戦相手を探しています…」画面。経過秒数と、同じ人数キューの待機人数を表示する。
3. 相手が見つかると自動で合流し、ロビー画面へ移る。ロビーIDは表示しない（見知らぬ人への乱入を防ぐため）。
4. 目標人数がそろうと **3秒カウントダウンののち自動で対戦開始**。全員が「準備完了」を押す操作は不要。
5. 4人戦で60秒たっても埋まらない場合、その時点の人数（2〜3人）で自動的に開始する。
6. 結果画面に「同じ面々で再戦」「別の相手を探す」「タイトルへ」を並べる。
7. 再戦で人数が足りなくなった部屋は、自動的に募集を再開して待機に戻る。

**待機が上限に達している場合**は2で入場できず、「今は混み合っています（待機 16/16）」と表示する。10秒ごとに自動で再試行し、その間ロビーIDを共有する通常対戦へ誘導する。空きが出れば自動的に探索へ進む。

### 3.1 ランダム部屋と通常ロビーの違い

| 項目 | 通常ロビー（ID共有） | ランダムマッチ |
| --- | --- | --- |
| 席数 | 常に4席、2〜4人で開始 | 選んだ人数（2または4）が上限 |
| 開始 | 全員の準備完了＋ホストが開始 | 人数が揃えば自動開始（4人戦は60秒で切り上げ） |
| 準備完了ボタン | あり | なし |
| ロビーでの武器変更 | できる | **できない**（変えたい人は退出して探し直す） |
| ロビーでのルール変更 | ホストがいつでも変更できる | **できない**（探す前に選ぶ） |
| ロビーIDの表示 | する | しない |
| 待合所への登録 | しない | する（入場券が要る） |

ランダム部屋で武器変更を禁じるのは、準備解除で自動開始が止まり、見知らぬ相手を待たせ続ける事故を防ぐため。装備はマッチ前に確定させる。

ルールも同じ理由でマッチ前に決める。ホストがひとりで待っている間は探索画面を出しているためロビーに触れられず、相手が来たあとは（2人戦なら3秒で）開始してしまうので、ロビーでの変更は実質的に機能しない。カウントダウン中に突然ルールが変わるのは参加者から見て事故でもある。

## 4. 待合所（Vercel + Upstash Redis）

### 4.1 なぜこの構成か

フロントと `/api/cutout` が既に Vercel にあるため、**同一オリジンのまま増やせて CORS もAPIキーの露出も考えなくてよい**。Redis の TTL・ソート済みセット・Lua スクリプトは、期限切れ・待ち行列・上限の原子的な判定という今回必要なものがそのまま揃っている。画像処理（HF Space）と資源を共有しないので、`cutout` の重い処理に巻き込まれない。

### 4.2 キー設計

| キー | 型 | 内容 | 期限 |
| --- | --- | --- | --- |
| `mm:tickets` | ZSET | member=券ID、score=失効時刻。**待機人数はこの集合の要素数** | 要素ごとに30秒（スクリプトが掃除） |
| `mm:queue:<2\|4>` | ZSET | member=roomId、score=募集開始時刻（古い順に配る） | 部屋のハッシュ消滅時に掃除 |
| `mm:room:<roomId>` | HASH | hostToken／targetSize／players／gameMode／phase／handedOutAt | 30秒（pollのたびに延長） |
| `mm:ip:<hash>` | STRING | 同一IPが保持する券の数 | 60秒 |

`mm:room:*` に実体を置き、`mm:queue:*` は順番だけを持つ。ハッシュが期限切れで消えていれば、その `roomId` は候補から外して ZSET からも削る。

### 4.3 エンドポイント（3つだけ）

`api/match/[action].js` の1関数で `enter`／`poll`／`leave` を受ける。**更新も取得も `poll` ひとつに集約する**のが要点で、券の延長・部屋の広告・候補の取得・待機数の取得を1往復で済ませ、KVのコマンド数を最小にする。

```jsonc
// POST /api/match/enter        入場（上限判定）
{ "protocolVersion": 3, "targetSize": 2 }
→ 200 { "ticket": "…", "waiting": 7, "max": 16 }
→ 429 { "error": "FULL", "waiting": 16, "max": 16, "retryAfter": 10 }

// POST /api/match/poll         探索中（roomId を持たない）
{ "ticket": "…", "targetSize": 2, "exclude": ["123456"] }
→ { "ok": true,
    "rooms": [ { "roomId": "482913", "players": 1, "gameMode": "0", "waitingSeconds": 12 } ],
    "waiting": { "total": 7, "2": 5, "4": 2 } }
→ { "ok": false, "reason": "EXPIRED" }      // 券が失効。enter からやり直す
→ { "ok": false, "reason": "ROOM_TAKEN" }   // そのロビーIDは他人が使用中

// POST /api/match/poll         ホストとして待機中（roomId を持つ）
{ "ticket": "…", "targetSize": 2, "roomId": "482913",
  "hostToken": "…", "players": 1, "gameMode": "0", "phase": "LOBBY" }
→ { "rooms": [ …自分より古い部屋があれば1件… ], "waiting": { … } }

// POST /api/match/leave        退場（券と部屋の後始末）
{ "ticket": "…", "roomId": "482913", "hostToken": "…" } → { "ok": true }
```

- `poll` に `roomId` を付け始めた時点で「探索中」から「ホスト」へ遷移する。状態は券が持つのでサーバー側に遷移の概念は要らない。
- `hostToken` は最初に `roomId` を送ったときにサーバーが発行し、以後その部屋を更新・削除できるのはその券だけになる。
- `phase` が `LOBBY` 以外、または `players >= targetSize` の部屋は候補から外す（部屋自体は残す）。
- 候補は**待ち時間が長い順**に最大3件。返した部屋は5秒間ほかの人へ返さない（同じ部屋への殺到を防ぐソフト予約）。
- ホストへ返す候補は「自分より先に待っている部屋」1件だけで、しかも**自分がまだ1人のときに限る**。ホストは移籍のために候補を見るだけなので、ソフト予約はかけない（探索者を待たせないため）。
- 応答の区別：満員・IP上限・連打は `429`（`Retry-After` 付き）、券の失効とID重複は `200` に `ok:false` を載せて返す。前者は待てば解決し、後者はクライアントの手順で解決するため。

### 4.4 上限の判定（Luaは使わない）

当初はLuaスクリプトで原子的に判定する予定だったが、それでは検証に実Redisが必要になり「テストしたコードと出荷するコードが別物」になる。代わりに**ZADDしてから自分の順位（ZRANK）を見る**方式を採る。

```
ZREMRANGEBYSCORE mm:tickets -inf <now>     期限切れの券を掃除
ZADD             mm:tickets <now+ttl> <券>  まず自分を並べる
ZRANK            mm:tickets <券>            自分が何番目か
ZRANGE           mm:tickets 0 -1            待機数の内訳（上限があるので常に小さい）
→ 順位 >= 上限 なら ZREM して「満員」を返す
```

これが競合下でも正しいのは、**後から入った人が必ず自分より後ろに並ぶ**ためである。スコア（＝有効期限）が同じミリ秒で並んだ場合に備え、券の先頭に `INCR mm:seq` で得た通し番号を埋めてある。Redisは同スコアをメンバー名の辞書順で並べるので、同点は必ず到着順に解決する。結果として新規入場者の順位は常に「現在の待機人数 − 1」になり、同時に入場しても順位は一意に定まる。

この通し番号を取るため `enter` だけHTTP往復が2回になる（1回目が `INCR`、2回目が上の並び）。`enter` は1セッションに1回なので、コストへの影響は無視できる。

同一IPの枚数制限も同じ仕組みを `mm:ip:<hash>` に対して使う。入場の連打は `SET mm:rate:<hash> 1 NX EX 5` で弾く。

### 4.5 コマンド予算と上限値の決め方

KVのコマンド数はほぼ `待機人数 × ポーリング回数` で決まる。ポーリング間隔は**探索中を短く、ホスト待機中を長く**する（ホストは相手から来るのを待つだけで、頻繁に探す必要がない）。

| 状態 | 間隔 | 1人あたり |
| --- | --- | --- |
| 探索中 | 4秒 | 15回／分 |
| ホストとして待機中 | 8秒 | 7.5回／分 |

平均11回／分とすると、**1日のコマンド数 ≒ 最大待機人数 × 11 × 60 × 稼働時間（時）**。

| 最大待機人数 | 1時間 | 2時間 | 4時間 |
| --- | --- | --- | --- |
| 8人 | 約5,300 | 約10,600 | 約21,100 |
| 16人 | 約10,600 | 約21,100 | 約42,200 |
| 32人 | 約21,100 | 約42,200 | 約84,500 |

Upstash の無料枠は日次のコマンド数に上限があるため（値は契約時に要確認）、**`MATCH_MAX_WAITING` は「想定する同時接続」ではなく「無料枠を割り算して出す値」**として決める。初期値は16を提案する。上限に達したときに断る仕組みがあるので、超過して課金されるより「混雑中」と伝えるほうが事故が小さい。

Vercel の関数呼び出し回数も消費するが、この規模では先にKVの上限に当たる。

### 4.6 上限を設けることの副作用（重要）

**上限があるということは、少数のリクエストでサービスを止められるということ**でもある。16人分の券を1台で取れば、正規の利用者は誰も入場できない。したがって上限とセットで次を必須とする。

- 同一IPが同時に持てる券は2枚まで（`mm:ip:<hash>`）。IPは保存せず、ソルト付きハッシュだけを持ち、60秒で消す。
- 券は30秒で失効する。タブを閉じた人の枠は自動的に空く。
- `enter` は同一IPから5秒に1回まで。超過は429。
- 満員を返すときも待機数は返すので、UIは「16/16」と正直に出せる。

## 5. クライアントの状態機械

`src/network/useRandomMatch.js`（新規）が次の状態を回す。

```
IDLE
 └ start(targetSize) → enter
FULL                 満員。10秒ごとに enter を再試行。ユーザーはいつでも中止できる
SEARCHING            4秒ごとに poll。候補があれば順に試す
 ├ 入室成功 → MATCHED
 ├ 失敗（満員・対戦中・無応答10秒）→ 次の候補 → 尽きたら SEARCHING 継続
 └ 候補なしが2回続く → HOSTING
HOSTING              部屋を作り、poll に roomId を載せて8秒ごとに広告し続ける
 ├ 誰か入ってきた → MATCHED
 └ 自分より古い部屋が候補に出たら、自分の募集を畳んでそちらへ移る
    （※自分の部屋が1人のときだけ）
MATCHED              leave で券を返し、以後は通常の部屋と同じ
CANCELLED            leave して IDLE へ
```

- **二重ホスト対策**：全員が同時にホストになると永久に出会えない。「自分より古い部屋へ移籍する」規則で、先に待ち始めた部屋に人が集まる。
- **券を返し忘れても**30秒で失効するため、枠が永久に埋まることはない。`leave` は `navigator.sendBeacon` でタブを閉じるときにも送る。
- **自分の部屋を引かない**：`exclude` に自分の `roomId` と直前に対戦した部屋を入れる。

## 7. 例外と受け止め方

| 状況 | 挙動 |
| --- | --- |
| 待機が上限に達している | `enter` が 429。「混雑中（16/16）」を表示し10秒ごとに再試行。通常ロビーへ誘導する |
| 券が失効した（スリープ復帰など） | `poll` が `EXPIRED`。`enter` からやり直す。満員なら FULL へ |
| 候補の部屋が満員・対戦中 | ホストが `REJECT` を返す。参加側は次の候補へ |
| 候補が無応答（タブを閉じた） | 10秒で打ち切り次の候補へ。部屋は30秒で待合所からも消える |
| 同じ部屋を2人が同時に引いた | 早い者勝ち。あぶれた側は次の候補へ（席は `reserve()` が同期的に確保する） |
| 集合後・開始前に誰かが抜けた | 自動開始を取り消し、募集を再開する |
| 対戦中に抜けた | 既存どおり脱落（`FORFEIT`）扱いで試合は続く |
| ホストが抜けた | 部屋は解散（既存の `CLOSED`）。残った人はタイトルへ戻り再検索できる |
| KVに繋がらない／無料枠切れ | 「ランダムマッチは今使えません」と表示し、ID共有の通常ロビーへ誘導する。**対戦そのものはP2Pなので、待合所が落ちても既存の遊び方は生きる** |

## 9. 判断が必要な残りの項目

- `MATCH_MAX_WAITING` の初期値（本案は16）。無料枠の日次コマンド上限を確認してから第4.5節の表で決める。
- ポーリング間隔（本案は探索4秒／ホスト8秒）。長くすればコストは下がるが、マッチ成立が遅くなる。
- 4人戦の切り上げ時間（本案は60秒）と、自動開始までの猶予（本案は3秒）。
- 同一IPが持てる券の枚数（本案は2枚）。同じ家から2人で遊ぶ場合を考えると、これ以上は必要か。
- 上限を全体で1つにするか、2人戦／4人戦で分けるか（本案は全体で1つ。内訳は `waiting` で返す）。

### 疎通確認

`scripts/check-match-kv.mjs` が本物のKVに対して「入場→部屋の登録→探索→ソフト予約→退場→後始末」を通しで試す。デプロイ前にローカルから実行できる。

```sh
UPSTASH_REDIS_REST_URL=https://xxx.upstash.io \
UPSTASH_REDIS_REST_TOKEN=AX... \
node scripts/check-match-kv.mjs
```

### 動かすのに必要な設定

Upstash でデータベースを1つ作り（リージョンは東京）、Vercel に次の環境変数を入れる。

| 変数 | 内容 |
| --- | --- |
| `UPSTASH_REDIS_REST_URL` | Upstash の REST URL |
| `UPSTASH_REDIS_REST_TOKEN` | 同トークン |
| `MATCH_MAX_WAITING` | 最大待機人数（既定16） |
| `MATCH_TICKET_TTL` | 券と部屋の有効秒数（既定30） |
| `MATCH_PER_IP_MAX` | 同一IPが持てる券（既定2） |
| `MATCH_IP_SALT` | IPをハッシュ化する際のソルト |

未設定なら `/api/match/*` は 503 を返し、ランダムマッチだけが無効になる（ID共有のロビーは影響を受けない）。
